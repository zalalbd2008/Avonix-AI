# Event Philosophy

> "Events describe what happened. They do not instruct what should happen."

---

# Purpose

This document defines the event philosophy used throughout the Avonix AI platform.

It establishes:

- What an event is
- When events are published
- Who owns events
- How modules collaborate through events
- Event naming conventions
- Event governance

This document does not define individual event schemas.

---

# What Is an Event?

An Event is a factual record that something has already happened.

Examples:

- Lead Created
- Conversation Closed
- Website Connected
- Knowledge Published
- AI Response Generated

Events describe completed business facts.

They are never commands.

---

# Why Events Exist

Events allow modules to collaborate without becoming tightly coupled.

Instead of:

```
CRM

↓

Calls

↓

Analytics
```

The platform prefers:

```
CRM

↓

Publishes Event

↓

Event Bus

↓

Analytics

Automation

Notifications

AI

Reporting
```

The event is the shared contract.

---

# Core Principles

Every event should be:

- Immutable
- Observable
- Auditable
- Versioned
- Business-focused
- Owned
- Traceable

---

# Event Lifecycle

```
Business Action

↓

Validation

↓

State Change

↓

Event Published

↓

Subscribers React

↓

Audit Recorded

↓

Metrics Updated
```

Events occur after successful state changes.

---

# Event Ownership

Every event has one canonical publisher.

Only the owner of the business entity may publish its lifecycle events.

Example:

| Entity | Event Publisher |
|---------|-----------------|
| Lead | CRM |
| Conversation | Conversations |
| Knowledge | Knowledge |
| Website | Website Management |
| User | Identity |
| Automation | Automation Engine |

Subscribers must never publish duplicate lifecycle events for the same transition.

---

# Event Categories

## Domain Events

Business events representing meaningful state changes.

Examples:

- Lead Created
- Website Connected
- Conversation Closed

---

## System Events

Infrastructure or operational events.

Examples:

- Cache Cleared
- Worker Restarted
- Job Completed

---

## Integration Events

Events exchanged with external systems.

Examples:

- Webhook Received
- Payment Confirmed
- Calendar Synced

---

## Security Events

Security-related activities.

Examples:

- Login Failed
- Threat Detected
- Permission Changed

---

## AI Events

Events generated by AI workflows.

Examples:

- Knowledge Indexed
- AI Response Generated
- Confidence Below Threshold

---

# Event Naming

Use the pattern:

```
domain.entity.action
```

Examples:

```
crm.lead.created

crm.lead.qualified

conversation.started

conversation.closed

knowledge.published

website.connected

website.health.changed

automation.completed

security.threat.detected
```

Naming should be:

- Predictable
- Stable
- Human-readable

---

# Event Payload Principles

Every event should include:

- Event ID
- Event Type
- Version
- Timestamp
- Actor
- Organization ID
- Website ID (if applicable)
- Entity ID
- Correlation ID
- Metadata

Sensitive data should not be embedded unnecessarily.

---

# Event Consumers

Subscribers may:

- React
- Notify
- Analyze
- Trigger automation
- Update dashboards
- Generate reports

Subscribers must not alter the original event.

---

# Event Ordering

Consumers should not assume perfect delivery order unless explicitly guaranteed.

Where ordering matters, use:

- Entity Version
- Sequence Number
- Timestamp
- Correlation ID

Business logic should remain resilient to delayed or repeated delivery.

---

# Idempotency

Consumers must safely process duplicate events.

Processing the same event twice should not create inconsistent business state.

---

# Event Versioning

Events evolve over time.

Rules:

- Existing fields remain stable whenever possible.
- New optional fields are preferred over breaking changes.
- Breaking changes require a new event version.

---

# Correlation

Related events should share a Correlation ID.

Example:

```
Conversation Started

↓

Lead Created

↓

Automation Triggered

↓

Notification Sent

↓

Appointment Booked
```

A shared Correlation ID enables complete journey tracing.

---

# Event Governance

Before introducing a new event, verify:

- Is it a business fact?
- Is there an existing event that already represents it?
- Does the owner publish it?
- Is the name consistent?
- Does it require versioning?
- Does it expose sensitive information?

---

# Anti-Patterns

Avoid:

- Command-like events
- Duplicate lifecycle events
- Technology-specific names
- Ownerless events
- Hidden side effects

Example:

❌ `runLeadWorkflow`

✅ `crm.lead.created`
